# 運転層の契約({{PRODUCT}} 運用プロファイル — 配員・設備台帳・停止語彙の記述規約)

正典: `{{METHOD}}/method/templates/product-profile/operator-layer.md`(本ファイルの配布元)。

> 本書は、工程を運ぶ者(**運転員** — 人・Bot・スクリプトを問わない)が読む**記述規約**である。
> 「誰が製造し、誰が検査し、いま工程は進めるのか止まるのか」を、既存の台帳から読み取れる形に固定する。
>
> 構造: **§1〜§7 は core(環境非依存)**。末尾の **adapter 区画** に配布元の環境固有の対応(機械化の所在・出自)を置く —
> core は環境を知らない。他の環境へ配布するときは adapter を差し替える(core は変えない)。
>
> **本書は記述の規約であり、これを読む機構の存在を主張しない**(§7)。

## 1. 三つの形式は台帳の射影 — 二重正本を作らない

運転層が扱う形式は 3 つだけで、いずれも**既存の台帳(変更台帳・変更指示書・検査報告・裁定記録)から導かれる射影**である。

| 形式 | 何を答えるか | 導出元 |
|---|---|---|
| job | この工程は今、進めるか・止まるか・誰へ渡すか | 変更台帳のエントリ+変更指示書(状態・配員・受入条件) |
| receipt | 直前の検査は何を測り、結果はどうだったか | 検査の実行記録(終了コード・対象の同一性) |
| ruling | 止まった工程を人間がどう裁いたか | 裁定記録(変更指示書の裁定節・議事) |

規則: 射影は**手書きしない**。射影の値と台帳の値が食い違ったら、正しいのは台帳であり、射影を直すのではなく台帳を直す。
射影を保存する場合は「非正本」と明記し、hash や判定語を台帳へ転写して正本にしない。

## 2. 停止語彙と配送先(固定表)

工程が進めないとき、その理由は次の 10 語のいずれかで表す。語ごとに「誰へ渡すか」が固定されている。
運転員は理由を**分類する**だけで、**解決しない**(解決は配送先の仕事)。

| 停止語彙 | 意味 | 配送先 |
|---|---|---|
| `NONE` | 進行可 | next(次工程) |
| `NORMATIVE_RULING` | 規範判断が要る(仕様・方針の裁定点) | human(人間) |
| `CONVERGENCE_LIMIT` | 収束しないまま反復上限に達した(再実行ではなく裁定点) | human |
| `VERIFICATION_FAIL` | 検査が赤 | factory(製造側へ差し戻し) |
| `BOM_CONTRADICTION` | BOM が自己矛盾している | designer(設計者) |
| `PREFLIGHT_HOLD` | 開始条件が成立していない(工程判定・製品判断ではない) | process(工程の所有者) |
| `LEDGER_INCONSISTENT` | 台帳と指示書の状態が矛盾している | ledger-owner(台帳の所有者) |
| `MISSING_INPUT` | 欠測(指示書不在・台帳が読めない)— **測定不能は合格ではない** | operator(運転員) |
| `INDEPENDENCE_FAIL` | 製造者と検査者が独立でない(§4) | operator(配員のやり直し) |
| `INSPECTION_MISSING` | 独立検査が要るのに、その結果が回収されていない | operator(独立検査の結果回収) |

規則: 語彙を増やさない・言い換えない。当てはまる語がないなら `NORMATIVE_RULING` として人間へ渡す(運転員が新語を作らない)。

## 3. 設備台帳の規約

製造・検査を行う主体(AI モデル・人間・スクリプト)は**設備**として台帳 `bomdd/70-equipment.yaml` に登録する。
設備は「誰」ではなく「何ができ、何が認定されているか」で記述する(工程 → 必要能力 → 使える設備、の順に決まる)。

- **id**: `EQ-NNN`(3 桁)。一度割り当てたら変更・再利用しない(使わなくなったら `status: retired`)。
- **独立性の 3 軸**: `model` / `harness` / `account_lineage`(モデル・実行ハーネス・アカウント系統)。§4 の判定に使う。
- **来歴(provenance)**: 各属性に 4 種のいずれかを付す — `self-reported`(設備自身の申告)/ `harness-measured`(ハーネスやログの機械記録)/
  `user-declared`(人間の宣言)/ `unknown`。来歴は監査欄であり、判定には値のみを使う(来歴で通過/停止を変えない)。
- **`unknown` は照合不能であって通過ではない**。値が unknown の軸を含む照合は成立させない(fail-closed)。
- **qualification_ref**: 設備認定(何の工程に対して、どの実験・記録で適格とされたか)への参照。未認定は `unqualified` と書く —
  空欄にしない(空欄は「認定済み」と「未記入」を区別できない)。
- **kind**: `ai-model` / `human` / `script`。人間も設備として登録する(独立性の判定に人間が含まれるため)。

## 4. 独立性の規則

製造者(producer)と検査者(inspector / executor)の独立は、設備台帳の宣言属性を照合して判定する。次のいずれかなら**不成立**:

1. 同一 id
2. 3 軸(model / harness / account_lineage)がすべて一致
3. いずれかの軸が `unknown`(照合不能)
4. producer が未宣言、または executor が台帳にない

主張しないこと: 本規則は**宣言上の照合**であり、独立性の実効(別主体が本当に別の判断をすること)を保証しない。
別の Bot を「セキュリティ境界」として扱わない — 独立検査は被覆を足す装置であって、境界ではない。

## 5. 配員の記述先

配員は 2 か所に**同じ id** で記述する(どちらか一方だけだと、射影の導出元が定まらない):

1. 変更台帳(`bomdd/60-change-register.yaml`)のエントリ: `producer: EQ-NNN` / `inspector: EQ-NNN`(任意・記述欄)。
2. 変更指示書(`bomdd/60-change-order-eco-NNN.md`)の「担当設備」節: `- producer: EQ-NNN` / `- inspector: EQ-NNN`。

`inspector` を書いた変更は「独立検査が要る」と宣言したことになり、その結果(§6 の判定語)が回収されるまで verified に上げない(§2 `INSPECTION_MISSING`)。
`inspector` を書かない変更は製造者の自己較正だけで閉じる(それが許される変更かどうかは変更管理の規律が決める)。

## 6. 判定語の契約(検査報告の先頭)

独立検査の報告は、機械でも人間でも同じ場所から判定を読めるよう、先頭を次の形に固定する:

- 先頭の handoff ヘッダ行(`[` で始まる行)0〜1 行と空行を飛ばし、**最初の非空行の行頭**が `ACCEPT` / `REJECT` / `UNMEASURABLE` のいずれか(大文字・行頭空白なし)。
- `REJECT` なら同じ行に所見番号を並べる。`UNMEASURABLE` なら原因と試みたことを本文に書く(合格に数えない)。
- 報告がなければ `MISSING`、上の形に合わなければ `UNPARSED`(散文は解釈しない)。どちらも判定ではなく「未回収」である。

## 7. 機構がない環境では人間の配員規律が担う

本書は「何を・どこに・どう書くか」を決める。**これを読んで工程を止める機構が製品リポに存在することを、本書は主張しない**。
機構がない環境では、§2 の分類・§4 の照合・§5 の記述・§6 の回収は、運転員(人間)が手で行い、その事実を変更指示書に書く。
機構の有無にかかわらず、台帳の記述は同じ形にしておく — 機構が後から来ても、台帳を書き直さなくて済むように。
