# 変更管理手順({{PRODUCT}} 運用プロファイル)

> 典拠: BomDD playbook §8(Phase 7)+`{{METHOD}}/method/prompts/phase7-change-order.md`。
> 本書はそれを本プロダクトの実運用へ写像した**運用プロファイル**であり、方法論と矛盾した場合は
> 方法論が正。運用で得た教訓の一般形は方法論リポへ還元する。
> 実証例: ViewPrism2 ECO-038(不具合修正)/ECO-039(裁定取り込み)。

## 0. 適用開始時期

本書が効くのは**初回納品後**(golden 承認済みの as-built がある状態)。それまでの初回製造は
フォワード・モード Phase 0〜6(`/bomdd-next` が入口)であり、ECO は使わない。
ただし process-core(保護パス `src/`・`test/`)を設置済みのリポでは、初回製造の成果物を保護パスへ置く commit も open な ECO を要求する(E01)。
その場合は初回製造を **ECO-001 として起票してから**製造 commit を行う(起票 commit が先・同一 commit 起票は不可。BomDD ECO-084・運転実証の実測)。

## 1. リポジトリの役割と変更の流れる方向

| リポ | 役割 | 変更の入口になるケース |
|---|---|---|
| BomDD 方法論(同梱 kit: `{{METHOD}}`・正本リポの出自は `bomdd.lock` の origin_path) | 方法論(法規・手順書・テンプレ) | 手順自体の欠陥・教訓の一般形昇格(送り先は正本リポ — kit は凍結写しにつき直接編集しない) |
| BomDD-Plm | PLM 工具(lint/viewer・DB なし・git が正本) | 準拠 findings → `bomdd/plm-intake/` 修復票(台帳が育ってから) |
| `{{CAD}}` | **CAD(設計原器)**: mock+screens docs+review_points 裁定 | 設計判断・視覚仕様・未確定事項の裁定 |
| `{{PRODUCT}}` | 製品: `bomdd/` 台帳+src+tests | ECO の実行と記録(本書の主対象) |

原則は一方向: **裁定・設計は CAD へ、実行・記録は製品へ、手順の改善は方法論へ**。
乖離時の権威: **製品の裁定台帳の個別裁定が最優先**(裁定は既定に優先する — ECO-023)。
未裁定の面は fidelity policy(`../{{CAD}}/docs/02_mock_fidelity_policy.md`)の既定に従う。

## 2. 共通規律(全シナリオ共通・違反は cheat 扱い)

- **R1 起票なき製品コード変更の禁止**。src/tests への diff は、register に対応する ECO
  エントリが先に存在しなければならない。(機械化候補: bomdd-lint R-052 diff_audit)
- **R2 修正着手前の工程診断**。所見はまず mock(CAD)/UI-IR/BOM/実装 のどの工程の欠陥かを
  診断し、上流欠陥なら上流(CAD→BOM)を先に直す。コードから入る経路は存在しない。
- **R3 スコープ外所見の「ついで修正」禁止**。工程内で見つけた別問題は
  (a) 51-cheat-log へ記録 (b) 分離起票 の二択のみ。現 ECO の diff に混ぜない。
- **R4 human gate は 2 つだけ**: **裁定**(裁定層= CAD・要求・仕様・E-BOM・K-BOM の設計判断と、その選択肢選び)と **golden**(実機承認)。
  AI は次の gate まで止まらずに進め、gate 到達時は「人間がやることはこれだけ」を明示して
  停止する。調査・起票・診断・プローブ・実装・機械受入・文書同期・register 更新は AI の作業。
  **導出層(M-BOM・Control Plan・Routing)の選択も AI の作業** — 是正案の選択・製造や検査の順序と計画・自分が作った成果物の直し方は、
  AI が決めて記録し、次の停止点で決定として報告する(裁定として問わない。異議はその停止点で受ける)。
  範囲の切り方(工程内で見つけた別問題を記録にするか分離起票にするか)も R3 の二択から AI が選ぶ — 現 ECO に混ぜることは R3 が禁じているので、混ぜたいときだけ人に問う。
  人へ戻すのは、裁定層を変えないと成り立たない場合、`{{METHOD}}/method/bomdd-playbook-v1.md` §4.5 が人へ戻すとした 3 種
  (新しい機能・新しい約束・導出不能)に当たる場合、charter・ECO で決めた上限(時間・回数)を超える場合だけ(BomDD ECO-106)。
  **上限に達したときの既定の処置**(設計合成〔converge〕の周回上限は除く — そちらは converge 手順 5 のとおり裁定点): 延長を求めて止まらず、
  確かめた部分を受入候補として示し、残りは既知の欠陥・既知の不正確として記録し、ECO の主張をその範囲まで縮めて次の停止点で報告する
  (片付けず・巻き戻さない。全緑でない diff は fix コミットにしない。上限を超えて続けるかは人が報告を見て決める — playbook §8.5・BomDD ECO-108)。
  R7 の並置が未了、または転写漏れが残る場合は R7 が優先する: golden に出さず、fix コミットにもせず(register の status 注記を
  「golden 待ち」・implemented にしない)、実施記録は書いたうえで status 注記と実施記録に「上限到達・golden 不可(R7)」と書いて止まる
  (停止語彙は `NORMATIVE_RULING` — 延長か打ち切りか、残った diff をどうするかは人が決める。BomDD ECO-110)。
- **R5 是正はプローブ先行**。欠陥是正は、是正前に不合格となる回帰テスト(または実測プローブ)で
  真因を裏取りしてからコードに触る。プローブが不合格にならなければ診断またはプローブが症状を捉えていない — コードに触らず R2 へ差し戻す(playbook §8.3)。
  R8 の見直しで出た所見のプローブは R8 に従う(確かめられない所見は記録して停止点で列挙)。
- **R6 既存固定オラクル行は変更しない**(回帰のヤードスティック)。変更分の受入は新規行として追加。
- **R7 セルフゴールデン(出荷前の原器並置)**。UI サーフェスに触れる fix は、golden 提示の**前**に
  AI 自身が是正対象の各サーフェスを CAD 視覚原器(captures)と並置し、差分を全列挙して
  「裁定済み許容差分/転写漏れ」に分類する。**転写漏れ 0 になるまで golden に出さない**。
  視覚 probe は CAD の視覚契約チェックリストから fix 時に**先行生成**する(golden 所見の後追い禁止)。
  共通契約(ダイアログ言語等)に触れた場合は、直した面でなく**契約×適用面マトリクスの該当列の全面**を
  検査対象にする。根拠: 機械受入は原器適合を検査せず、原器の同梱は「参照可能」であって「参照強制」
  ではない(playbook §8.3 / ViewPrism2 GF-072-01→073-01/03/04/07 の転写漏れ連鎖)。
- **R8 製品コードの変更は独立レビューを受ける**(candidate・BomDD ECO-103)。保護パス(`src/`・`test/`)に触れる ECO は、
  golden の提示(golden n/a なら受入の依頼)の**前**に、製造した文脈と別の新しい文脈で diff を見直す。所見は**全列挙**し、
  スコープ内の所見は層で分けて**既定の処置**を当てる(playbook §8.5・BomDD ECO-108):
  - **実体**(製品の成果物 — コード・テスト・プローブのソースとその振る舞い)= R5 へ戻って是正。プローブが不合格にならず確かめられない所見は、
    所見とプローブを記録して停止点で列挙する(R2 への差し戻しは ECO 本来の症状のプローブに限る)。
  - **証拠**(実行結果と観測 — テスト結果・キャプチャ・並置)= 読めれば受入、読めなければ `UNKNOWN` と記録して合格の根拠にしない
    (読めて不合格・skip を示すものは実体へ)。
  - **記録**(それ以外 — ECO 本文・台帳・報告の記述など)= 既知の不正確として記録し、是正しない。ただし主張・合否を実際より広く述べるものは
    主張を縮めて処置し、機械検査を赤にするものは是正する。スコープ外= R3。
  - **見直しは 2 回まで**(§8.5 の実測で効いた束縛「第 2 回で最後」。1 回目に実体の所見がなければそこで終わる)。最後の見直しで残った実体の所見は
    修理せず、停止点で**既知の欠陥**として示し、ECO の主張をそれのない範囲に縮める(受け入れるかは golden〔golden n/a なら受入の依頼〕で人が決める。
    受け入れられた既知の欠陥は、その後 R3 の二択で記録か分離起票にする)。例外: R7 の転写漏れは持ち越さない — 是正し、R7 の並置で確かめる(3 回目の見直しはしない)。
    その是正は eco-fix の手順 1〜3.5(機械受入と並置を含む)を通し、3.6 だけを通らない(BomDD ECO-110)。
  - 1 回の見直しは 1 つの diff に対して行う。その回に含める見直し(並行するものを含む)は回を始めるときに記録し、
    その結果がそろうまで是正を始めない。回収できない見直しは `MISSING`(合格ではない)と記録してその回を閉じる。
    結果を 1 つも回収できなかった回は見直しに数えない — やり直し、やり直せなければ停止点で `MISSING` を示して主張を「R8 未レビュー」とする。
    閉じた後に届いた結果もその回の所見として同じ層で扱い、次に所見を処置する時点で処置する(最後の回が閉じた後なら実体は既知の欠陥として
    停止点で示す — R7 の転写漏れは除き、R8 の例外のとおり是正する。ECO の適用後なら R3)。各回が見た diff を記録する(commit、未 commit なら stage して
    `git write-tree` の tree — BomDD ECO-110)。
  - 既定を外れる処置(2 回を超える見直し・上の場合以外の記録層の是正)は次の停止点で人が決める(§8.5。それまでは既定の処置を当てて進む)。
    golden の不合格・受入の差し戻しから戻った是正は 1 回目から数え直す。
  - 見直しの回数の上限に達しても工程は止まらない(停止語彙は `NONE`)— 既定の処置を当てて既存の停止点へ進む(R4 の ECO の上限とは別)。設備の独立が要る場合は、
    その検査が 2 回を担う(1 回目= 境界探索・2 回目= 是正確認+回帰 — `factory-delegate` の range。1 回目に実体の所見がなくても 2 回目を行う)。
    最後の回の REJECT は、残った所見とともに既知の欠陥と同じく停止点で示す。

  **実体の所見が残ったまま停止点へ進むのは、上限(R8 の見直しの上限・R4 の ECO の上限)に達した場合と、プローブで確かめられない所見だけ。**
  文書のみの変更、または機械的な 1 行の変更は「R8 対象外」を宣言して省略できる(宣言は製造者が書く — 自分の判断であることが記録に残る)。
  **独立は 2 段**: **文脈の独立**(R8 の既定 — 同じ設備の別の新しい文脈でよい)/ **設備の独立**(`operator-layer.md` §4 —
  モデル・ハーネス・系統のいずれかが異なる)。設備の独立は playbook §3 の場合(高リスクの検査治具の新設・検査意味論の変更など)に要る。
  レビューの記録には、どちらの独立かとレビューした設備を書く。設備の独立でない見直しは register の `inspector` に書かない
  (§4 で不成立になる)。R4 の人の関門は増やさない — 1 人が要求者・裁定者・golden 承認者を兼ねてよいが、それを独立した人の
  承認とは主張しない。由来: ViewPrism2(eco-fix 3.7・src に触れた fix・2026-07-18)と ViewTube(R8・product-source の変更)が、それぞれ別に、
  製品コードの変更を別の新しい文脈で見直す規則を置いた(`test/` を含めたのは本 R8 の決め)。
  文脈の独立で足りるかは**未測定**(BomDD EXP-20261010-01)。

## 3. シナリオ別経路

| シナリオ | 入口 | human gate |
|---|---|---|
| 1. 新機能追加 | 要求(REQ 追加) | 裁定+golden |
| 2. 既存機能拡張 | 要求 or 未確定事項(review_points) | 裁定+golden |
| 3. 不具合修正 | 症状の観測 | (症状報告)+golden |
| 4. OSS セキュリティ | アドバイザリ(CVE 等) | 処置裁定 |

### 3.1 新機能追加 — CAD から入る

1. 要求を REQ として受理(Phase 1 の根拠精度規律)。
2. **CAD 先行**: `{{CAD}}` で mock+screens を原器化し、設計裁定(review_points)を人間が確定。← gate①
3. 製品側 ECO 起票(`/eco-file`)→ 影響分析 → BOM 改訂(**オラクル・ファースト**: 受入行を先に追加)。
4. 製造 → 機械受入(CLAUDE.md の受入コマンド全緑)。
5. golden(実機)← gate② → `/eco-accept` でクローズ+台帳同期。

### 3.2 既存機能拡張 — 新機能+read-across

経路は 3.1 と同じ。追加規律:
- **既存 golden の再検査範囲を影響分析で事前宣言**する(共有コンテナ/共有 VM を触る場合、
  非表示状態=条件付き可視の裏面も対象)。
- 未確定事項の裁定を伴う場合、裁定はまず CAD の review_points で確定してから製品 ECO に
  取り込む(CAD コミットが先)。

### 3.3 不具合修正 — 診断から入る

1. `/eco-file <症状>`: 採番 → 症状記録(再現手順・観測日・「事実」と「疑い(未検証)」の分離)→
   **工程診断(R2)**: CAD に定義があるか/BOM は健全か/実装が逸脱か。混入コミットの特定も試みる。
2. 診断分岐: 実装逸脱→製品側の欠陥是正 ECO / CAD 未定義・曖昧→**先に CAD を是正・裁定**(gate①)/
   検査器・台帳の欠陥→該当上流成果物の是正 ECO(doc-only もあり得る)。
3. `/eco-fix <ECO>`: **プローブ先行(R5)** → 最小是正(**真因構造を消す案を優先**)→ 機械受入 →
   golden 合格基準を提示して停止(gate②)。
4. `/eco-accept <ECO>`: クローズ 3 点セット(検査観点明記=再発防止・register applied・
   本文クローズ節+教訓)。

### 3.4 OSS セキュリティ — 台帳の逆引きから入る

1. `/sec-advisory <アドバイザリ>`: K-BOM/Service BOM を逆引きし、**パッケージグラフの実測**
   (アドバイザリ本文+scratch 交換検証)を一次資料に影響を判定(BOM トレースだけに頼らない)。
2. 処置裁定(gate①): (a) **調達交換のみ**= fresh 工場を使わず**設計者適用+全再認証** /
   (b) コード変更を伴う = 3.3 の経路へ合流 / (c) 影響なし=根拠つきで記録のみ。
3. いずれも ECO として register に記録(発生源= DEG イベントを明記)。

## 4. コミット規約(ECO ライフサイクル)

固定製造証拠への後発の受入追記は、`{{METHOD}}/method/acceptance-evidence.md`の
**独立append-only受入証拠レイヤー**として扱う。Control Planの拡張・合成ではない。
製品の導入ECOで適用範囲・開始版・記録形式・必須検査器を固定し、検証してから使う。
CP/Oracle/製造receiptは不変とし、基準の実変更は通常ECOへ戻す。
未移行の歴史を改作しない。未配備を受入可能として扱わず、詳細はeco-accept手順1に従う。

| 段階 | prefix | 内容 |
|---|---|---|
| 起票 | `起票(eco-NNN):` | ECO 本文+register エントリ(staged)。診断結果を要約 |
| 裁定 | `decide(eco-NNN):` | 選択肢の裁定記録(実装なし) |
| 是正 | `fix(eco-NNN):` | コード+テスト+本文実施記録。機械受入結果を要約 |
| 受入 | `accept(eco-NNN):` | golden 合格・クローズ 3 点セット |

## 5. 導線(スキル)

作業者は自由文プロンプトではなく、以下のスキルを入口にする(`.claude/skills/`)。
各スキルは対応する手順を実行し、**human gate で「人間がやること」を明示して停止**する(R4)。

| スキル | 対応 | 停止点 |
|---|---|---|
| `/bomdd-next` | フォワード Phase 0〜6(納品前の入口) | 各フェーズの human gate |
| `/eco-file` | 起票+工程診断(§3 全シナリオの入口) | 診断分岐の提示(裁定要なら gate①) |
| `/eco-fix` | プローブ先行の是正+機械受入 | golden 合格基準の提示(gate②) |
| `/eco-accept` | golden 合格後のクローズ 3 点セット | 完了報告 |
| `/sec-advisory` | OSS アドバイザリの逆引き+処置選択肢 | 処置裁定の提示(gate①) |
