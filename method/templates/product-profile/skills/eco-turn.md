# /eco-turn — 周の引き渡しと、反応の受け取り(candidate・BomDD ECO-126)

典拠: [bomdd/change-management.md](../../../bomdd/change-management.md) §3.5。
引数: ECO 番号(例: `eco-012`)。

人の番は増やしていない。golden(実機で確かめる番)を、2 つの形で使う: **周ごとの利用(合否を求めない)** と、
**確認項目(合否)**(R4)。このスキルは、その 2 つの止まり方と、あいだの振り分けを持つ。製造そのものは /eco-fix である。

## 前提確認

1. 起票(/eco-file)の gate① で、人が「周で回す」と名指し、周の上限・費用の枠・起きてはならないことの一覧が承認されていること。
2. この周の候補が、/eco-fix の手順 1〜5 を通って commit されていること(機械受入は全緑。赤のままの版は渡さない)。
   手順 4 の実施記録は周ごとに書き、register の status 注記は「周 N 候補・利用待ち」とする(status そのものは変えない)。
3. 周の記録 `bomdd/loops/eco-NNN.yaml` があること(無ければ、ここで作る — 書式は `{{METHOD}}/method/tools/loop-count.py` の冒頭)。

## 1. 渡す(周ごと)

渡すものは 5 つ。長い一覧にしない。

1. **起動の仕方**: `{{METHOD}}/method/tools/handover-stamp.py stamp` で作った起動口(launch)を渡す。どの版かを人が画面で
   見分けられる印(題名など)があれば、それも書く。利用者の設定やデータに触れない版(保存先を外へ向けた版)で渡す。
2. **変えたこと**: 5 行まで。製造側が仮に決めたものには、そう書く。
3. **機械が確かめたこと・確かめていないこと**: 見ていない動き(手の操作・動く画面など)は、名前を挙げる。
4. **索引**: 仮の決定と、別の文脈の読みで見つかったもの。**問いではない** — 違和感が出たときに原因を辿るためのもの、と書く。
5. **返事の形**(下の 2)。

渡したら、周の記録に、版の組(commit・治具の sha256・主なファイルの sha256)と渡した時刻を書く。
版ごとに別のフォルダへ置く(同じフォルダに stamp し直すと、前の版の起動は今の版に数えない)。

**返事が来たら、まず `handover-stamp.py check` を走らせ**、最後の `record line`(`launches: {count: N, matching: M}`)を、
周の記録の `launches` に**そのまま**写す(exit 0・1・3 のどれでも写す):

- exit 0 — 渡した版が起動口から動いた。そのまま進む(分かるのは、起動口から起動した回についてだけ。起動口を通さない起動は
  見えない — 道具の冒頭の限界)。
- exit 1 — 渡した版と違うものが動いたか、ファイルが変わっている(例: `{count: 2, matching: 1}`)。その返事を、渡した版への
  反応として扱わない。どの版で使ったかを人に伺う(伺ったら、周の記録の `reasks` に 1 を足す)。
- exit 3 — 起動口からの起動が無い(**不明**。`{count: 0, matching: 0}`)。反応の行は書くが、その返事を合格の根拠にしない:
  どの版で使ったかを人に伺う(`reasks` に 1 を足す)。区分(`class`)の語は増やさない — 不明は `launches` の欄が示す。
- exit 2 — 測れない(起動口を作っていない・`handover.json` や跡が壊れている)。写せる record line は無いので
  `launches: unknown` と書き、exit 3 と同じに扱う。

## 2. 返事の形

合否は求めない。ただし、言葉に種類を付けてもらえる形で渡す:

- **合格** — このままでよい。
- **合格だが直したい** — 目的には届いている。好みや使い勝手で、変えたい所がある。
- **不合格** — 目的に届いていない。

種類は人が付ける。返事に種類が無いときは、製造側の読みで付けてよいが、周の記録に `kind_by: reading` と書く
(人が付けた `kind_by: user` と分けて数える)。名指しが要る返事(未解決の報告の受け入れ)は、**番号を書ける形**で伺う —
一語のボタンだけにしない。

## 3. 反応を振り分ける

周の記録には、**返事 1 つにつき 1 行以上**を書く。人が違うと言った事は、1 つの事につき 1 行。違いが無い返事も 1 行
(区分は `none`)。区分は、検査の結果ではなく、まず**発話が何を言っているか**で分ける(括弧は、周の記録の `class` に書く語)。

| 発話が言っていること | 区分 | 戻り先 |
|---|---|---|
| 図面にある決定と、違うものを望んでいる | 決定の変更(`decision_change`) | 図面に改訂の行・台帳に人の決め 1 件。次の周。その決定を固定した検査は置き換える(§3.5 の条件) |
| 図面に無いものを望んでいる | 新しい望み(`new_want`) | 要求の表に発話つきで足す。次の周(§3.5 の条件) |
| 動かない・おかしい・期待と違う気がする | 症状 — 下の表で決まる | 書いてある文(図面・人の決め・要求)から検査を書き、渡した組で走らせる |
| 直したい所はあるが、今回は直さなくてよい | そのまま(`left_as_is`) | 記録だけ |
| 違うと言った事が無い | なし(`none`) | — |

症状の検査の結果:

| 結果 | 区分 | 戻り先 |
|---|---|---|
| 同じ手順で赤になる(再現できる) | 修理(`repair`) | /eco-fix の手順 1 へ(検査を保って直す) |
| 赤にならない・再現できない | 未解決の報告(`unresolved`) | 「修理ではない」とも「不具合は無い」とも書かない。発話・試した検査・何が分かれば決まるかを番号つきで記録し、受入の前の一覧に載せる |
| 原因がこの変更の外だと、確かめた事実で言える | 変更の外(`outside`) | 記録。直すなら分離起票(R3) |

- 新しい望みや決定の変更で、要求・仕様など裁定層のファイルを変えるとき: 裁定層を保護している製品(`ruled_layer`)では、
  その commit に `BomDD-ECO-Ruling: <この ECO>` の trailer と、指示書の Sources read 節での `path:line` の引用が要る(検査器 E13)。
- 問いの形の発話は、方向として受け取ってよいが、**裁定には上げない**。閉じるのは確認項目の返事。
- 手の感覚に関わる違い(速すぎる・合わせにくい など)は、境目の数を推測で変える前に、手の動きを記録して数える。
- 反応ごとに、種類・誰が付けたか・区分・**何に行き着いたか**(製造側の決定 / 作り手の決定 / 読みの指摘 / なし)・
  **それは使う前の引き渡しに載っていたか**を、周の記録に書く。次の引き渡しに「発話 → 区分」の表を載せる。

周の上限か、費用の枠に達したら、延ばさずに止めて報告する(確かめた部分と、残ったものを示す — R4 の上限の処置)。

## 4. 「よい」の後 — 確認項目を渡す前の条件

人が「合格」と言ったら、その組を記録し、次を確かめる(1 つでも欠ければ渡さない):

| # | 条件 |
|---|---|
| P1 | 受入の組(治具なしの通常のビルド)で、受入基準が全部通っている |
| P2 | 並置で転写漏れが 0(R7) |
| P3 | 別の新しい文脈で 1 回読んである(R8)。指摘は、直したか、下の一覧に入れてある |
| P4 | 台帳に、止める印のある未決が無い。単独で立てた未決が、確認項目に 1 つずつ入っている。`ui-cad-gate.py` が通る |
| P5 | 「よい」の組と受入の組の差が、確認項目に入っている |
| P6 | 2 つの一覧ができている: **未確認の細部**(確認項目が覆わない仮の決定 — 人がすることは無い)と、**未解決の報告**(頼んだ機能が、場面によってうまく動かないかもしれないもの — 人が受け入れるものを名指す) |

状態が 3 つの製品(staged → implemented → applied)では、ここで `implemented` への遷移の commit(fix の trailer つき)を置く
(状態が 2 つの製品では要らない — change-management.md §4)。確認項目から周へ戻れるのは、`implemented` が profile の
`open_states` に入っている製品だけ(入っていなければ、戻りの周の保護パスの変更を検査器が E01 で拒む。戻っても status は
`implemented` のまま — BomDD ECO-126 の V4 で、両方を足場の製品で実測)。

そのうえで、**確認項目(操作・見るもの・由来)**と未解決の報告の一覧を渡して止まる。**このとき**、register の status 注記を
「golden 待ち」にする(確認項目の返事を待つあいだの印。status そのものは変えない)。確認項目の文は、製造側の決定から
写さず、**人が読める時に何が見えるか**で書く(動き出し・止まり際・中くらいの速さを見込む)。

周の記録の行き先(`disposition`)との対応: 確認項目か単独の裁定に入れた行 = `to_user_check` / 未解決の報告に入れた行 =
`to_user_report`(`reports` にも 1 行)/ 未確認の細部に入れた行 = `no_action`。ほかの語と、`kind`・`outcome` の語の意味は、
`{{METHOD}}/method/tools/loop-count.py` の冒頭「語の意味」にある。

振り分けで「人がすることは無い」に回した指摘が、後の反応と結び付いたら、周の記録の行に `outcome: tied_to_diff` と書く
(数えるため。回した判断の当否を、後で読めるようにする)。

## 5. 受入の条件

| # | 条件 |
|---|---|
| A1 | 確認項目への返事が合格。試していない番号は合格に数えない(任意と示した項目は、開いたままと記録する) |
| A2 | 未解決の報告の 1 件ずつに「受け入れる・直す周へ戻る・この変更の主張から外す」が決まっている。受け入れるものは人が名指した |
| A3 | 台帳の未決が 0 件。仮の決定の束は、`status: ruled`・`ruling: accept-as-built`・`decided_by: user`(受入の返事をした人)で閉じ、evidence に「確認項目が覆った決定」と「作ったままの決定」を分けて書く — 作ったままの決定を、人が中身を見て決めたとは書かない。**数えて確かめる** — ゲートは、止める印の無い未決が残っていても通る |
| A4 | `ui-cad-gate.py` が通る。`loop-count.py --check` が exit 0 |

(A1〜A4 は、このスキルの受入の条件の番号。変更管理手順の R1〜R8 とは別。)

満たせば /eco-accept eco-NNN へ(register の status 注記は、確認項目を渡した時に「golden 待ち」にしてある — 上の 4)。
「直す周へ戻る」があれば、status 注記を「周 N 候補・利用待ち」に戻し、直して候補を commit し、変えた差分を別の文脈で 1 回読み、
P1〜P6 をやり直して、変えた所と合格でなかった項目をもう一度渡す(この戻りも 1 周に数える)。

## 停止点

- 周の引き渡し(1)と、確認項目の引き渡し(4)で止まる。どちらも「人がやることはこれだけ」を明示する。
- 起動の前後で、利用者の設定・データのフォルダが変わっていたら、直ちに止めて報告する(版を渡さない)。

## スコープ外所見(R3)

周の中で見つけた別の問題は、§3.5 の条件に当たる新しい望みを除き、現 ECO に混ぜない。分離起票か 51-cheat-log 記録の二択。
