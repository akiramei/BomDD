# /calibrate — 測定系較正ループ(証拠品質+検査器検査)

正典: `{{METHOD}}/method/templates/product-profile/skills/calibrate.md`(本ファイルの配布元)。
関連: `{{METHOD}}/method/bomdd-playbook-v1.md` §4.4(受入の設計 — 較正・被覆・限界宣言の正本)・
§6.4(帰属の順序)・§8.3(是正報告の裏取り)・`{{METHOD}}/method/cheat-taxonomy.md`(帳簿代用 LP)。

目的: 検査の緑を無条件に信頼へ変換しない。「テストが通った」と「主張が証明された」の間の
距離を、昇格の**前**に測る。`/converge` と対をなす — あちらは**設計の収束**、こちらは
**証拠の資格査定**。どちらも人間の仕事を裁定だけに戻すための工程入口である。

出自: 計器欠陥は製品欠陥と独立に反復する。実測: CI が赤のまま 11 コミット潜伏
(BomDD ECO-020)/ 検査結果の観測前に push が実行(BomDD ECO-024)/ 新設ゲートが同一弧内で
偽陽性と過剰免除を連発(BomDD ECO-033→034)/ 宣言 fixture への参照 0 件のまま全行緑+
human golden 合格(TimetableAdv ECO-037→038)。査定の教義は playbook §4.4 に正本があるのに
事故は起きた — **教義の存在は工程投入を保証しない**。本スキルはその工程入口である。

## 自発起動契約(この節が正本)

次のイベントを認識したら、人間の呼び出しがなくても本手順を適用する:

1. ECO の verification・受入・較正の節を**書くとき**(全 ECO で必ず起きるイベント)
2. 既存の緑を主張の根拠に**引用するとき**(「全 PASS」「テスト済み」を前提に置く文を書くとき)
3. 検査器(validator・gate・fixture・CI 定義・期待表)を**新設・変更した直後**
4. 検査器の偽陽性・偽陰性・沈黙インシデントの**後**

> 注意: 散文の自発起動は保証されない(`/converge` で非起動 2 回の実測 — BomDD ECO-033)。
> **起動したこと自体を成果物に残す**(較正 receipt)ことで、非起動と「起動したが所見ゼロ」を
> 区別する。非起動の機械観測(gate 化)は必要が実測されてから判断する(§8.5)。

> トリガーの機械アンカー可能性(分類のみ — gate 化はしない): 1・3 はリポジトリ側から
> 観測可能(hard trigger 候補= verification artifact・検査器の変更)。2・4 は認識依存
> (semantic trigger)。gate 化は**本スキルの非起動が実測されてから**判断する — 先回りの
> gate が偽陽性デッドロックを生んだ実測がある(BomDD ECO-033→034)。

## 適用範囲

- **使う**: 上記イベント。**機械受入の証拠そのものが対象** — `/eco-fix` のプローブ→受入という
  手続きの存在は証拠の品質を保証しない(受入 5 項目成立の同一弧内で計器欠陥が 2 度検出された
  実測= BomDD ECO-033→034)。
- **使わない**: 設計合成の収束(`/converge` の領分 — 収束機構の二重化は工程の無駄)。
  `/eco-accept` のクローズ事務そのもの(本スキルはその**前段**= 証拠の資格査定)。
  証拠を伴わない事実照会。
- **用語**: playbook §4.4 の「較正(negative control)」は凍結前の一工程の名。本スキルの
  「測定系較正」はそれを**含む**査定工程であり、§4.4 の工程を置換しない。

## 手順

1. **主張の同定** — この緑/赤が根拠になる主張を 1 文で書く。主張が書けない証拠は装飾であり、
   昇格の根拠に使わない。

2. **検査 battery** — 該当する行だけを選んで問い、判定を記録する。詳細規定は正本(右列)。

   | # | 問い | 正本 |
   |---|---|---|
   | Q1 | 検査文(検査名・docstring・報告文)はコードが測る以上を主張していないか。乖離したら**コードを主張へ広げる**(狭めない)— 本問の対象は**検査文**(計器の自己記述・主張の正本は仕様)。昇格主張側の過大は手順 4 の帰結で扱う(縮小の採否は裁定に属する) | §4.4 |
   | Q2 | reference で較正したか — known-bad で**赤**・known-good で**緑**を対で実測し(「常に赤」の計器と弁別)、期待は事前宣言か。**good/bad のラベルは被較正計器から独立した根拠**(植込んだ食い違い・凍結要求・人間 golden・別系統 oracle・既知の過去故障)で確定しているか | §4.4 較正・三点様式 |
   | Q3 | 弁別力の成立を被覆と誤読していないか — **契約の各項が独立に落ちる**ことを示したか | §4.4 |
   | Q4 | 宣言入力(fixture・test_vectors)は実入力か(ablation)。宣言 source から effective behavior までの lineage は閉じているか | §4.4・cheat-taxonomy LP |
   | Q5 | UNKNOWN を PASS に数えていないか(未実行・実行不能・権限不足・別 commit の結果・空集合) | AGENTS.md 規律 4・6 |
   | Q6 | 検査結果は**観測されてから**後続操作に使われたか(条件で結んだか) | AGENTS.md 規律 3 |
   | Q7 | 常設検査器に陽性対照はあるか — 「沈黙」と「健全」を区別できるか | §4.4 |
   | Q8 | 予防ゲートの偽陽性に**根拠つき出口**があるか。免除は数えて表示されるか | BomDD ECO-034 |
   | Q9 | 計器の個体参照は現物か(対象個体の識別を刻印し、期待個体と突合したか) | §4.4 |
   | Q10 | 検出力の限界(**実施した検査が測っていない次元**)を宣言したか。未了リストは代用にならない | §4.4 |
   | Q11 | 計器の系統誤差に関わる**意味的に異なる入力クラス**を分けて測ったか — 集計・順位の緑はクラス別の系統誤差を吸収して隠す(既知実例: use/mention クラス — 検査を論じる文書だけが系統的に誤判定された) | §4.4 同等性受入・BomDD ECO-034 |

3. **帰属と是正の経路** — battery で欠陥が出たら、まず計器帰属か製品帰属かを分ける
   (§6.4 — `harness_bug` を先に消してから工場能力を疑う)。計器欠陥は ECO で起票する —
   検査器が捕捉しないことは許可ではないし、**判定を書き換えて通すことは決してしない**。

4. **判定と receipt** — 各主張を**二軸**で判定し、較正 receipt を成果物へ埋め込む。
   - **測定成立性**: **observed**(測定は成立した)/ **unknown**(未実行・実行不能・
     権限不足・別 commit の結果・空集合 — **理由コード必須**)。**unknown に資格判定を
     付けない** — 測っていないものに資格は無く、その証拠は根拠として**使用不可**
     (測定不能は合格ではない)。
   - **証拠資格**(observed のときだけ): **適格** / **条件付き適格**〔測っていない次元を
     明記〕/ **不適格**。判定対象は命題の真偽ではなく**証拠の資格** — 緑は「仕様が
     証明された」を意味しない。
   「条件付き適格」のまま昇格させる場合は、測っていない次元を昇格先の記録に残す。
   **不適格**の証拠は、その主張の昇格根拠として使用しない — 帰結は**証拠追加 / 主張縮小 /
   必要時の裁定上申**のいずれかを選ぶ(判定に帰結を持たせる)。ただし「不適格」判定
   そのものは査定全体の FAIL ではない — 主張単位で閉じる。

## 較正 receipt(成果物に埋め込む)

- 査定した主張と判定(**測定成立性×証拠資格**・要点のみ・`file:line` または実行コマンド)
- 検出した計器欠陥と帰属(なければ「なし」と明記)
- 宣言した検出力の限界 — 実施した検査が**測っていない次元**

提示物の中の一節として埋め込む(ECO なら verification 節内)。新しい artifact 置場は作らない。

## 学習ループ(停止点)

計器欠陥が本手順の**外**で発覚したら(人間の指摘・独立検査・実運用の偽陽性/偽陰性)、
その欠陥を上の失敗型へ分類する。

- **既知の型**なら手順 2〜3 の実施漏れ。原因を receipt の記録とともに報告する。
- **新しい型**なら**表 B へ追記を提案する** — 追記の実施も ECO 経由
  (検査器が捕捉しないことは許可ではない)。
- 表 B の型が**製品名を落としても成立する**と判断できたら、`/lesson-promote` で方法論側へ
  昇格を提案する(表 A への反映は方法論リポの ECO)。
