## 1. 試行の設計(凍結・1 機能・1 製品= ViewPrism2)

**既存の機構だけで行う**(並行する承認台帳を増やさない): 約束= 10-requirements の REQ(新設・`classification_hint: maintainability`)/ 承認= register の起票→承認(人)/
設計リリース= `bom_rev` の更新と tag / E/S の結線= 30-ebom の `requirement_refs`・53 の item に `service_requirement_refs`(1 欄・candidate)/ 導出先= 32-mbom の unit・33-control-plan の行 / 実行証拠= ECO-143 の `cp_results`。

手順(順序が重要):
1. **人が裁定する(上流)**: 対象 1 機能について、保守上の約束を**人の言葉**で 1〜3 文に書く(交換してよい部品とその条件 / 交換・更新後も保つ挙動 / 復旧の手段と許容する損失 / 許容する保守境界)。
   統括 AI は約束の候補を提示してよいが、**約束の内容は人が確定**する(本 ECO §5 の裁定)。
2. **REQ として固定**: 約束を REQ(1〜3 件)に書く(G1 の根拠精度: 受入の深さと許容差を決められる精度まで)。対象 E 品目の `requirement_refs` に加える。53 の対象 item に `service_requirement_refs` を置く。
   この時点の E/S を **設計リリース**(bom_rev +1・tag)として固定し、register に「承認済み E/S 版」として記録する。
3. **統括 AI が導出する**: 承認済み E/S 版から、M-BOM unit の対応(新設か既存か)と Control Plan の行(交換・復旧・継続の検査: 深さ・治具・許容差・落ちたときの振り分け〔製品修正 / 測定系復旧〕)を導出する。
   導出で**人へ戻す判断**は「新しい機能・新しい保守の約束・導出できない判断」だけ。機械的な派生(行の追加・ID の採番・治具の指定)は承認対象にしない。戻した判断は種別つきで記録する(M1)。
4. **製造**: 製品側 ECO(ViewPrism2 ECO-144〔仮〕)で、導出した CP 行の検査(テスト・trait cp)を工場に製造させる。製品の挙動は変えない(約束の検査を足すだけ)— 既存オラクル無接触。
5. **追跡**: 承認済み REQ → E → M → CP → test ID(trait cp)→ 実行証拠(`cp_results` の行・対象 digest)を 1 表にする(M2)。**構造上の到達性**(各辺の実在)と**期待値の意味の妥当性**(約束を本当に検査しているか)は
   別に審査する(前者= 機械・後者= 人)。
6. **振り分けのリハーサル**: 導出した CP 行を 1 本、意図的に赤(製品側の違反)と測定不能(治具の不能)にして、`cp_results` の区分と承認依頼で**製品修正 / 測定系復旧**へ振り分けられることを 1 回ずつ観測する(M3)。
   欠測・未知 CP ID のリハーサル(EXP-20261002-01 の補助注記)も同時に行える。
7. **E/M の責任境界の確認(論点 2)**: 対象機能で、E の機能 ID と約束(REQ)が M の ID に依存していないこと(参照方向= CP/M → E・E → M なし)を静的に確認する(M4)。
   M の再編を**実施はしない**(1 機能の試行で再編は過剰・参照方向の確認で代替)。

**採らない**: 新しい承認台帳・設計リリース文書の新設 / 全製品・全機能への適用 / DI・adapter の一律強制 / playbook・テンプレの改訂(評価の後)/ M の再編の実施 / 効果量の推定(N=1)。
