# ECO-VT-228 — 復元したバックアップの旧い条件が、次に起動するまで変換されない

- 状態: staged
- 起票: 2026-10-05
- 起票の根拠: ECO-VT-227 の独立レビュー第一回の所見 F1 への利用者の判断（2026-10-05、第 1 節）。基準点は `7781b33d`
- 診断層: implementation（第 3 節）
- 記録: 所見の出どころは ECO-VT-227 の独立レビュー第一回である（その記録は ECO-VT-227 の修理のコミットに入る）。この号の測定は読み取りだけで、実行していない（第 2 節）
- 種類: 欠陥の疑いの修理（`bomdd/process/change-management.md` の 3.2）。実行で確かめていないので、最初の仕事は赤くなる検査を作ることである

## 1. 依頼と判断

- **きっかけ。** ECO-VT-227 は、M-BOM にだけ書かれていた決めを要件と仕様へ書き戻す号である。その決めの一つは M-BOM の文「a restored backup is converted on its open」だった。書き戻した文を別の文脈の読み手が確かめ、コードがそのとおりに動かない経路があると報告した（所見 F1、blocking）
- **利用者の判断（利用者の言葉のまま、2026-10-05）。** 「A 復元経路の ECO も起票して」。選択肢 A の説明は「ECO-VT-227 からその決めを外し、復元の経路を別の号にする。赤くなる検査を先に作る」だった
- **利用者が選ばなかった道。** 事実に合わせた弱い文（「次に起動したときに変換される」）を要件に書き、起動までの空白を既知の欠陥として記録する。先に再現を確かめてから決める

## 2. 観察した事実（読み取りだけ。基準点 `7781b33d`、2026-10-05）

二人（ECO-VT-227 のレビュー役と、この号を起票した担当）がコードを読んで同じ結論になった。**実行はしていない。**

- **旧い条件の変換は、初期化からしか呼ばれない。** `CarryNodeRestrictionsAsync` の呼び出しは `src/ViewTube.Infrastructure/Persistence/SqliteCatalogStore.cs:150`（`InitializeAsync` の中）の 1 か所だけである（`git grep CarryNodeRestrictionsAsync -- src` で、呼び出し 1 と定義 1）
- **復元は初期化をやり直さない。** `RestoreAsync`（同 `:2125` から）は、復元したファイルが `InitializeAsync` を通っておらず、これからも通らないと自分の注記に書いている（同 `:2162` からの注記）。そのため、後から足した三つ（`AddRefreshOptOutColumnAsync`、`AddViewApplicationPoliciesTableAsync`、`AddAppSettingsTableAsync`）を復元の中で自分で当てている。旧い条件の変換は、その並びに無い
- **復元の後、画面は読み込み直すだけである。** `src/ViewTube.App/ShellViewModel.cs:8214` は `LoadLocalAsync` を呼ぶ。`InitializeAsync` の呼び出しは、起動時（同 `:3582`、`ViewTubeApplication.cs:219`）と MCP の起動（`src/ViewTube.Mcp/CatalogTools.cs:59`）だけである
- **読み込みは、旧い条件を黙って落とす。** ビューの階層は一つの JSON で、今のモデルのノードに Restriction は無い。変換を通っていない JSON を読むと、旧い条件は Condition にも DroppedRestriction にもならずに消える（レビュー役の読み。`ToView`、同 `:2856` 付近）
- **この経路を通す検査は無い。** 変換の検査（`test/ViewTube.Acceptance/NodeConditionPerTypeTests.cs:388` 付近）は、動いているファイルを書き換えて `InitializeAsync` を二回呼ぶ。復元の後の変換を確かめる検査は見つからなかった
- **同じ形の四回目である。** `RestoreAsync` の注記（同 `:2170` 付近）は、復元に手当てを足し忘れたのが三回目だと書いている。この号はその次に当たる
- **対象になるバックアップ。** 条件の形が入った ECO-VT-212 の修理（`d75a1b65`、2026-09-29）より前に取られ、スキーマの版が 4（`0d0a9f20`、2026-09-07 から）のもの。それより古いものは復元が受け付けない
- **仮説（裏づけなし）。**
  - 復元の直後、起動し直すまで、旧い条件を持つビューは条件なしで表示され、絞り込まれる。知らせは出ない
  - その間にビューを保存すると、旧い条件は書き落とされ、次の起動で変換するものが残らない（条件が失われる）。保存の経路は読んでいない
  - 起動し直せば（保存していなければ）変換される

## 3. 診断

層は実装である。

- 要件（REQ-032）は「この形より前に保存された条件は、結果を保つ」と言う。バックアップの中の条件を別に扱うとは言っていない。復元の後に変換されないなら、要件に合っていない
- M-BOM（`bomdd/32-mbom.yaml` の M-INFRA-PERSISTENCE-001、ECO-VT-212 の行）は「a restored backup is converted on its open」と書く。アプリの中の復元については、その文は起動し直すまで成り立たない。M-BOM の文も直す対象である
- 図面の層は関係しない。検査の層には、この経路の検査が無いという欠けがある

## 4. 守るべき振る舞いと検査

- **振る舞い。** 対象のバックアップを復元したら、起動し直さなくても、旧い条件は REQ-032 の決めのとおりに変換される（運べないものは捨てて、そのビューが知らせる）。二回目に開いたときに変換するものは残らない
- **検査。** 旧い条件を持つスキーマ 4 のカタログをバックアップとして用意し、復元してから、起動し直さずにビューを読む。修理の前は赤（条件が無い）、後は緑になること。復元 → 保存 → 起動し直し、の順でも条件が残ること
- **修理の形。** 修理のときに測ってから決める。復元の並びに変換を足すか、復元の後に初期化の追加の手当てをまとめて通す形にするか（同じ足し忘れが四回目なので、形を変える理由がある）を比べる

## 5. 範囲の外

- ECO-VT-227 の書き戻し（この決めは ECO-VT-227 から外した。修理の後に、要件へ書く文を決める）
- ビューパックの読み取りの経路（ECO-VT-227 のレビューは、こちらはコードと合っていると確かめた）
- スキーマの版が 4 より古いバックアップを受け付けるようにすること
