## 3. 分類(上から順に最初に当たったもの)

コマンドの文字列(Monitor は入力全体)に当てる。

| 順 | 分類 | 条件 |
|---|---|---|
| 1 | human_wait | 待ち時間が 3600 秒を超える(人の承認待ち・不在とみなし、合計に入れない) |
| 2 | commit | `git … commit`(フックの時間を含む) |
| 3 | supervised | `run-supervised-tests` |
| 4 | sweep | `sweep-capture-plans` |
| 5 | capture | `CaptureHarness`・`capture<数字>`・`all-plans`・`tiers<数字>`・`--plan` |
| 6 | mutation | `mutat` |
| 7 | targeted_test | `dotnet test`・`run-class`・`--filter` |
| 8 | validate | `validate_*.py`・`selftest_` |
| 9 | build | `dotnet build` |
| 10 | other | 上のどれでもない |

Monitor(背景の実行を待つ)は同じ分類を当て、`wait:` を前につけて別に集計する。背景で始めた呼び出し自身の待ち時間は、ほぼ 0 になる。

**commit のフックの判定(Q2)**: tool_result の本文に
`capture-plan sweep: a path that can strand a plan is staged` があれば「全計画あり」、
`capture-plan sweep: no path` があれば「全計画なし」、どちらも無ければ「不明」(出力を `tail` で切っていた場合など)。

**止めた回数(Q3)**: tool_result の本文に `commit blocked` を含む呼び出し。理由はその行の文字列で分ける。

## 4. 結果の読み方(数える前に決めた)

- commit のフック(検証器と全計画)の待ちが、全体の受け入れテストと撮影の比較の待ちより大きければ、
  遅さの主因は「全体の E2E」ではなく commit ごとの門である。是正の候補は、門を走らせる時機と検証器の速さになる。
- 撮影の比較(変更前と変更後の 2 回)の待ちが最大なら、変更前の側の撮影の使い回しが候補になる。
- 門が実際の不良(計画が最後まで走らない・検証の違反)で commit を止めていれば、その門には検出の実績がある。
  時間だけで門を外す判断をしない。

## 5. この測定の限界(先に書く)

- 待ち時間には、許可のプロンプトへの人の応答の時間が混ざる。1 時間を超えるものだけを除き、それ未満は区別できない。
- 並列に走った呼び出し(サブエージェントの同時実行)は、壁時計としては重複して数える。
- 分類はコマンドの文字列による。スクリプトの名前が分類の語を含まない重い実行は、other に落ちる。
- エージェントが考えている時間・書いている時間は数えない(ツールの待ちだけ)。
