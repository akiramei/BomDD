## 4. 結果の読み方(数える前に決めた)

- commit のフック(検証器と全計画)の待ちが、全体の受け入れテストと撮影の比較の待ちより大きければ、
  遅さの主因は「全体の E2E」ではなく commit ごとの門である。是正の候補は、門を走らせる時機と検証器の速さになる。
- 撮影の比較(変更前と変更後の 2 回)の待ちが最大なら、変更前の側の撮影の使い回しが候補になる。
- 門が実際の不良(計画が最後まで走らない・検証の違反)で commit を止めていれば、その門には検出の実績がある。
  時間だけで門を外す判断をしない。

## 5. この測定の限界(先に書く)

- 待ち時間には、許可のプロンプトへの人の応答の時間が混ざる。1 時間を超えるものだけを除き、それ未満は区別できない。
- 並列に走った呼び出し(サブエージェントの同時実行)は、壁時計としては重複して数える。
- 分類はコマンドの文字列による。スクリプトの名前が分類の語を含まない重い実行は、other に落ちる。
- エージェントが考えている時間・書いている時間は数えない(ツールの待ちだけ)。

## 8. 読み方(§4 の事前の決めに当てる)

- **遅さの主因は「全体の E2E」ではなく、commit ごとの門である。** commit(フックを含む)と単独の検証器の待ちは、本体の待ちの 62% を占める。
  一方、全体の受け入れテストは 1.0%、撮影の比較は 3.4% だった。§4 の第 1 項に当たり、是正の候補は、門を走らせる時機と検証器の速さになる。
- **「わずかな変更でも全体」は、半分は当たっている。** `src/` に触れる commit 14 件は、毎回、撮影の全計画を走らせた(1 回 4〜6 分)。
  ただし、より大きいのは、全計画を走らせない 154 件の commit が毎回払う検証器の時間である(中央値 約 2 分)。その半分(77 件)は、修理の前に書く経路を宣言する probe の commit だった。
- **撮影の比較の使い回し(§4 の第 2 項)は、この窓では優先度が低い。** 撮影の比較は 3.4% だった。
- **門には検出の実績がある(§4 の第 3 項)。** 30 回止め、そのうち撮影の全計画の 1 件は、道具の宣言の誤りを commit の前に捕まえた。残りは記録と工程の規則の違反である。
  時間だけを理由に門を外す根拠にはならない。問いは「同じ検出を、より少ない回数・より速い検証器で得られるか」である。
- **全体の受け入れテストは、この窓では製品の欠陥を 0 件見つけた**(16 回中、失敗の 2 回は原因不明の 1 件と環境の推定 12 件)。ただし約 3 日(2026-10-07T00:00Z〜10-10T03:00Z 頃)・1 製品の窓であり、「全体テストは不要」を支えるには足りない。
