## 起票(2026-07-27)

### 事実(実測)

- **失敗は C11 の 1 件のみ**。C1〜C10・C9(.NET スイート 4 本= 14/14・15/15・26/30 期待赤 4 件
  一致・9/9)は全 PASS。3 ジョブ(fast ubuntu / fast windows / dotnet)で同一。
- **根因**: CI ランナーに git の `user.name` / `user.email` が無い。C11 は `bomdd-init` を
  `--no-qualify` のみで呼ぶため git 経路を通り、初回 commit が identity 不在で失敗する。
  C4 は `--no-git` を渡すため無事。**C11 が「git identity が存在する」という前提を暗黙に持ち、
  その前提を環境へ委ねていた**。
- **潜伏**: 最後の緑= `9c255c7`(2026-07-24 11:00)。赤化= `ba9f325`(ECO-015 accept・
  2026-07-25 16:17)= **C11 を導入した ECO-015 の accept 時点から赤**。以後
  **11 コミット・約 2 日・ECO-015/016/017/018/019 の 5 ECO を跨いで赤のまま**。
- **失敗の現れ方は途中で変化した**(根因は同一):
  - ECO-015〜016: bomdd-init は commit 失敗を非致命(exit 0)→ C11 の `head_ok`(HEAD 実在)が
    False で FAIL。
  - ECO-017(REV-06)以降: git 経路失敗を致命化 → bomdd-init 自体が exit 1 で FAIL。
    **ECO-017 の是正が原因ではない**(現れ方を変えただけ)。

### 見逃しの構造(本 ECO の本体)

1. **CI の結果を一度も確認していなかった**。各 ECO でローカル self-conformance 全 PASS を
   確認して検証完了としていた。ECO-006 で CI を常設した目的(一括検証の入口)に対し、
   **結果を観測する経路が結線されていない**ため設備が実質無効化されていた。
   → ViewTube guide §6「入口はあるが hook がない / validator はあるが呼ばれない」と同型。
   **OBS-20260726-02(装置・操作対象・結線の三点)の 3 例目**(装置=CI・操作対象=検査は
   あり、**結線=結果の観測**のみ欠落)。
2. **ECO-017 の受入は「新挙動の発火」は確認したが「既存呼出し元への影響」を見なかった**。
   V2(e) で「git identity なし → exit 1」を検証しながら、影響分析には「CI 利用者は `--no-git` を
   明示」と書いた — **自分(C11)がその CI 利用者である**ことに気づいていない。
   silence §16(d)・OBS-20260713-01(影響分析の被覆と欠陥の被覆は同じ盲点を共有する)の実例。
3. **独立検査 3 ラウンドも指摘しなかった**。検査官は read-only でリポ内コードを見ており、
   **CI 実行結果というリポ外の観測面は視野に入らない**。FINDINGS §11.6「閉鎖にはリポ外アンカーが
   要る」の**裏面**: リポ外へ置いたものはリポ内検査からも見えない。

## 是正方針案(製造前・凍結前の草案)

1. **C11 の環境依存を除去**(推奨案 a): C11 が `bomdd-init` を起動する際、subprocess の env へ
   `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL` / `GIT_COMMITTER_NAME` / `GIT_COMMITTER_EMAIL` を
   与える。**検査は自分の前提を自分で満たす** — ローカルと CI の環境差が消える。
   - 代案 b(CI ワークフローで `git config --global`)は前提がローカル/CI の二重管理になるため
     採らない。代案 c(bomdd-init に fallback identity)は**ユーザーの identity を勝手に決める**
     ことになるため不可(製品挙動は変えない)。
2. **CI 結果確認の結線**(本 ECO の主目的): push 後に CI 結果を確認する規律を①暗黙知から
   ②以上へ引き上げる。**裁定点**(下記)で水準を決める。
3. **赤の潜伏を検出する仕組み**の要否も裁定に含める(例: 直近 push の CI 結論を self-conformance
   や還元手順が参照する — ただし**リポ内検査がリポ外状態へ依存する**設計になるため、
   fail-closed の方向と測定不能の扱いを慎重に決める必要がある)。

## 裁定を要する設計点(gate ① で裁定)

1. **CI 結果確認の水準**: (a)②散文(playbook / CLAUDE.md の運用規則に「push 後に CI を確認」)/
   (b)③入口コマンド化(push を含む手順スキルへ確認ステップを組み込む)/ (c)④機械化
   (直近 CI 結論を検査が参照)。**推奨= (a)+(b)**。(c) はリポ内検査をリポ外状態に依存させる
   ため、**測定不能(API 不達・未実行)の扱い**を誤ると新たな fail-open/誤 FAIL を生む — 本 ECO では
   採らず、観測として記録する。
2. **C11 の identity 値**: 固定値(`bomdd-selfconf` 等)を検査側で与える。**推奨= 採用**
   (scaffold は使い捨て temp ディレクトリのため実害なし・値を検査に固定すると決定性も上がる)。

## 教訓(還元候補 — lesson-promote 経由)

- **検査は自分の前提を自分で満たす** — 前提(identity・ロケール・タイムゾーン・ネットワーク)の
  充足を ambient な環境へ委ねると、「開発機では緑・CI では赤」という環境差が生まれ、
  **どちらか一方しか見ていない**運用では潜伏する。
- **常設した検査設備は「結果を観測する経路」まで結線して初めて機能する** — 装置(CI)と
  操作対象(検査)があっても、結論を見る手順が無ければ設備は無効化される
  (OBS-20260726-02 の三点=装置・操作対象・**結線**の 3 例目)。
- **リポ外の観測面はリポ内検査の視野に入らない** — 独立検査 3 ラウンド(read-only・リポ内)も
  CI 赤を指摘しなかった。FINDINGS §11.6「閉鎖にはリポ外アンカーが要る」の**裏面**。
