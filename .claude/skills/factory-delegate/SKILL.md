## 絶対規律

- **正本委譲**: 工場へ渡すのは手書き要約でなく **ECO/work order ファイルそのもの**(パスを読ませる)。
  要約は伝言ゲームで意味がずれる(ECO-137 で下書きが対象プロジェクト・要求内容とも誤っていた実例)。
- **完了バリア前に検査しない**: 委譲は非同期で、`/codex:status` は信頼できない(ECO-137 で別ジョブを
  completed 表示・実装ジョブは追跡外・"完了"後もファイル書き込みが継続)。**独立レビューは製造完了を
  ツリーで確認してから開始する**(製造と検査の時間的重なりが偽陽性 race を生む)。
- **無断コミット禁止**: 工場もこのスキルもコミットしない。受入ゲート通過後、独立レビュー→人/別 AI の
  裁定を経てから lifecycle クローズ(BomDD-ECO-Fix/Accept trailer)。
- **役割分離**: 製造(工場)・独立受入検査(異系統)・裁定(人)を分ける(transfer-04 の型)。
  同一 AI が製造と自己受入だけで閉じない。

## 手順

### 工程 0 — 前提チェック(委譲前)

- `/codex` が使える状態か(未認証なら `/codex:setup` を案内して停止)。
- 委譲対象 ECO が **staged**(起票済み・gate① 裁定要なら裁定済み)か。未起票なら先に起票。
- **正本と着手条件の突合**: ECO 本文 §4 是正方針・§5 影響 BOM・§6 残ゲートを読み、工場へ渡す
  ブリーフが正本と一致するか自分で確認する(下書き要約の誤りをここで潰す)。

### 工程 1 — 工場ブリーフの生成

下記テンプレを ECO から埋める。**src/tests の具体パス**と**受入 4 点**を必ず含める。

```text
<製品リポ名> の <ECO-ID> を実装してください。リポジトリ: <絶対パス>

- work order の正本: <bomdd/60-change-order-eco-NNN.md>(特に §4 是正方針)。要約でなくこのファイルを読んで作業すること
- 対象: <src の具体パス>(+ <tests の具体パス>)。<スコープ外にする同型箇所があれば「実測で要否判断」と明記>
- 要求: <§4 案の 1〜2 文要約。ただし詳細は正本参照>。<挙動制約: 例「missing 判定は bit 一致」>
- プローブ先行(red-first): 是正前に fail するプローブを先に書き fail を確認してから是正する
  (計数/操作回数プローブ+挙動同値プローブ。既存の同型テストに倣う。固定時間閾値のテストは書かない)
- 制約: 外部挙動・公開 API 不変(内部シグネチャは可)/ 凍結オラクル(<Oracle 名>)無接触 /
  diff は §5 影響 BOM の範囲内 / <リポ固有の lint・規約があれば列挙>
- 受入(全て実行し結果を報告): dotnet build(0 warning)・<Tests 名>(全緑)・<Oracle 名>(緑・無接触)・
  <validator: 例 python bomdd/validate_bom.py>(0-0)
- コミットはしないこと(レビュー後にこちらで行う)
```

### 工程 2 — 委譲(/codex を包む・ハーネス依存部)

- **Agent ツール**で `subagent_type: "codex:codex-rescue"` を呼び、上記ブリーフ+作業ディレクトリ明示を
  prompt に渡す(rescue.md の転送役規約に従う)。同期実行なら `--wait` を prompt 先頭へ。
- **返り値の task-id は信用しない**(ECO-137 で返り ID と追跡ジョブがずれた)。ジョブ特定は
  `node "<codex-companion.mjs>" status`(引数なし=一覧)で最新ジョブを見る。
- 委譲は 1 回で完結させる。**入れ子委譲禁止・並行製造で同一ファイルを設計者と工場が同時に触らない**
  (§8.1 隔離規律)。
- **経路が止まったときの切替**(BomDD ECO-062 弧・2026-09-10 の実測): companion 経路(app-server)は
  既定モデルが CLI 版より新しい・runner のプロトコル版不一致で**製造物と無関係に**止まることがある。
  切替先= CLI 直接 `codex exec -s <read-only|workspace-write> -m <model> -C <repo> -o <出力> -`
  (ブリーフを stdin で正本委譲・最終メッセージを CLI が出力ファイルへ書く= 当方は転記しない)。
  read-only は OS temp も書けず統合試験が unknown になる → 一時 git リポが要る検査は workspace-write。
  最終報告がプロバイダのコンテンツフィルタで遮断されることがある(語= 改竄・ACL・sandbox 等)→ ブリーフで
  中立語(環境制約・実行基盤)を指示し、遮断されたら `codex exec resume --last -`(`-o` なし・stdout から切り出す)。
  工場の後片付けコマンドは policy で拒否されうる → OS temp の残置は委譲側が確認して削除する。

### 工程 3 — 製造完了バリア(検査開始前・最重要)

`/codex:status` の "completed" を信用せず、**ツリーで製造完了を判定**する:

1. `git status --short` で変更ファイル群を把握。
2. **mtime 安定**: 対象ファイルの mtime を 2 回(15〜30 秒あけて)取り、変化が止まっているか確認
   (書き込み継続中なら待つ)。
3. **git ロック不在**+**codex ジョブが done**(status 一覧で参考確認。ただし一次判定はツリー)。
4. これらが揃って初めて「製造完了・独立レビュー可」と宣言する。

### 工程 4 — 受入ゲート(客観・機械真実)

安定ツリー上で 4 点を**自分で再実測**(工場の自己申告値は信用せず裏取り。ECO-137 で工場が 936 と申告し
初回測定が 934〔書き込み途中〕だった):

- `dotnet build` = 0 error / 0 warning
- 単体テスト = 全緑(数値を記録)
- 凍結オラクル = 緑かつ**無接触**(R6)
- リポ validator(例 `validate_bom.py`)= 0-0

いずれか赤なら工場へ差し戻し(帰属: harness_bug を先に消してから工場能力を疑う)。

### 工程 5 — 独立レビュー引き渡し(停止点)

**ここで停止し、異系統独立受入検査へ渡す**(自分が続けて裁定しない)。レビュー観点:

- **§5 影響 BOM との突合(63 diff 監査)**: 実 diff が宣言影響集合の内か。範囲外 diff=過剰変更。
- **案超過の検出**: work order の案を超える新規アルゴリズム・共有部品への波及がないか。あれば
  gate① 条項(「意味論差が出る場合は軽微裁定へ切替」)に該当しないか判定し、**maintainer へ上申**。
- **自己検証が張り損なう 4 類型**(transfer-04): meta-failure(ハーネスが測る経路に繋がっていない)/
  未検枝 / 存在 vs 完全性(申告した lint・テストが実在するか)/ 副経路。
- **工場の自己申告の裏取り**: §実施記録の数値・lint・テストの実在を実測で確認(申告と実測の乖離は所見)。

### 工程 6 — lifecycle クローズ(裁定後)

裁定を得てから 2 段でコミット(commit-msg hook が trailer を強制):

- fix: register `staged→implemented` + `BomDD-ECO-Fix: ECO-NNN`
- accept: register `implemented→applied` + gate②裁定(golden/n-a)+ `BomDD-ECO-Accept: ECO-NNN`

## この委譲自体の教訓(ECO-137 から)

- **正本委譲は機能した**: Codex は §4 案A を正しく実装し、未検証だった false-missing クラスまで自力で解いた。
- **完了バリアの不在が最大の失敗**: 書き込み途中版を読み偽陽性 3 件(lint 不在・テスト数・プローブ空虚)を
  出した。安定版で全件 refute。→ 工程 3 を必須化。
- **/codex status は一次判定に使えない**: 別ジョブを completed 表示。→ ツリー(mtime+gates)を一次真実に。
- **golden n/a の意味**: 挙動 bit 一致+視覚変更なし=実機に照合対象なし。「修正が些末」ではない。
  性能 ECO でも操作回数プローブ+挙動同値+direct-call lint で golden 不要にできる(ECO-134 の型)。
